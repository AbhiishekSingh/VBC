# VBC — Vendor Intelligence Platform

Vendor onboarding due-diligence for Indian vendors. The system automates the
**data layer**; a named analyst retains the **decision layer**.

```
backend/    FastAPI + PostgreSQL + Celery   (domain core + database complete)
frontend/   React + TypeScript + Vite       (complete, runs on mock data)
```

**133 tests passing** — 81 Python (48 scoring/policy, 33 database against real
PostgreSQL) and 52 TypeScript parity.

## Run it

```bash
# Frontend — works standalone, no backend required
cd frontend
npm install
npm run dev            # http://localhost:5173

# Backend
cd backend
pip install -r requirements.txt
python -m pytest                    # 81 tests (DB tests skip without a server)

# Database
export VBC_DATABASE_URL="postgresql+psycopg://user:pass@host/vbc"
python -m alembic upgrade head      # schema + immutability triggers
python -m app.db.seed               # catalog — idempotent, safe every deploy
```

See `backend/app/db/README.md` for the schema rationale, the deployment
privilege model, and the open PII question.

## The single-source-of-truth rule

The Python catalog in `backend/app/catalog/` is authoritative for every SCAN
parameter, option string, rating, weight, check definition and risk rule. The
TypeScript copies are **generated**:

```bash
cd frontend && npm run codegen
```

This writes `src/catalog/generated.ts`, `src/api/fixtures.ts` and
`src/scoring/parity-expected.json`. None of the three may be hand-edited.
CI runs `npm run codegen:check`, which fails the build if the committed files
differ from what the Python source produces — because a frontend that scores a
vendor differently from the backend is the worst bug this product can have.

## Two scoring implementations, one answer

`frontend/src/scoring/` mirrors `backend/app/domain/scoring.py` so the SCAN
page can recalculate as an analyst clicks, without a round-trip per click.
It is **preview only** — nothing it computes is persisted, and the server
recomputes on save.

`npm test` runs 52 parity assertions comparing the TypeScript engine against
outputs generated by the Python engine, across all three fixtures, every
pillar breakdown, every ledger line and every policy verdict. A failure there
means the browser and the server disagree about a vendor. Fix the divergence;
never adjust the expectation.

## Regression fixtures

The three seeded vendors are the contract. Their numbers must not move:

| Vendor | SCAN | Risk |
|---|---|---|
| #234478 Azahan Advertising | 0.90 / 1.50 · 60.0% | 50 DEEP REVIEW |
| #234479 Meridian Packaging | 3.80 / 3.90 · 97.4% | 95 APPROVE |
| #234480 Kaveri Traders | 0.40 / 1.10 · 36.4% | 30 REJECT |

## The coverage floor (§18.1) — still an open decision

SCAN excludes N/A parameters from both sides, so a thin audit scores against a
small bar. Azahan reaches exactly 60.0% on 6 of 18 parameters and the prototype
recommended onboarding it; a human overrode that.

The gate is implemented as `CoveragePolicy`, not hardcoded, because the client
has not decided and the decision cannot change once vendors are on file. Every
verdict records its `policyVersion`; scores from different versions are not
comparable.

* `PROTOTYPE_POLICY` — nothing gated, reproduces the signed-off behaviour
* `DEFAULT_POLICY` — the handoff's recommendation: ≥2 Assessment parameters
  and ≥8 applicable parameters before any positive verdict

Gating is one-directional. A Negative is never gated — thin evidence must not
manufacture a rejection.

## Known documentation defect

§6 of the project handoff states Kaveri "scored 62.5% and passed" without its
manual GST entry. That does not reproduce: Kaveri fails at 36.4%, 40.0% and
45.5% across all three configurations. The 62.5% belongs to an earlier build.
Both facts are asserted in `test_scoring.py` so the claim cannot quietly
return. Do not use the 62.5% flip in client-facing material.

## Reconstruction — why the schema exceeds handoff §13

§13 says `raw_response` makes a historical score reconstructable. That covers
the evidence but not the rules: `check_definitions`, `scan_parameters` and
`risk_rules` are mutable, so enabling GST in 2027 would silently make a 2026
score irreproducible.

Two tables close that: `catalog_versions` (immutable, content-hashed snapshot
of the whole catalog) and `vendor_scores` (immutable score snapshot citing its
catalog and policy versions). Decisions cite a score snapshot, never a live
recomputation.

## Immutability is triggers *and* privileges

`audit_log`, `vendor_scores`, `catalog_versions` and `decisions` reject UPDATE
and DELETE by trigger. But **TRUNCATE bypasses row-level triggers** and the
table owner can drop them — so the application must connect as a role that
owns nothing and holds only SELECT/INSERT on those tables. The GRANT block is
in `app/db/immutability.sql`; the gap is asserted in
`test_truncate_bypasses_the_append_only_guard` so it cannot be forgotten.
